# MEDDxAgent clinical backend

This is the application-facing runtime around the existing MEDDxAgent research engine. It does not replace DDxDriver, the diagnosis agent, the history prompt, or the RAG implementation.

## Runtime contract

The default clinical configuration is packaged at `ddxdriver/clinical/clinical.yml` and uses:

- interactive human-in-the-loop history taking
- OpenChoice DDxDriver after history completion
- PubMed SearchRAG
- SingleLLMCOT diagnosis
- no benchmark patient agent
- no benchmark ground truth or few-shot cases

The repository copy at `configs/clinical.yml` mirrors the packaged default and CI checks that they remain identical.

## Environment

Required by the default model configuration:

```text
OAI_KEY
```

Recommended for PubMed/NCBI Entrez:

```text
NCBI_EMAIL
```

Optional:

```text
NCBI_API_KEY
MEDDX_ALLOWED_ORIGINS
MEDDX_CLINICAL_CONFIG
PORT
```

`MEDDX_ALLOWED_ORIGINS` defaults to:

```text
http://localhost:5173,https://meddxagentfrontend.vercel.app
```

## Start command

After installing the project and the repository's documented Torch version:

```bash
meddx-clinical-api
```

The server reads `PORT`, defaulting to `8000`.

A host-agnostic `Dockerfile` is included for deployment platforms that build containers.

## Railway deployment

The repository includes `railway.toml` for the first connected clinical deployment. Railway is configured to:

- build the root `Dockerfile`
- check `GET /api/v1/health` before promoting a deployment
- allow up to 300 seconds for startup/health verification
- restart on process failure

Create one Railway service from `BoweloIpspace/meddxagent` using the `main` branch. Keep the service at its default single replica because clinical session state is process-local in this integration slice.

Set these Railway service variables before testing the clinical API:

```text
OAI_KEY=<required>
NCBI_EMAIL=<recommended>
NCBI_API_KEY=<optional>
MEDDX_ALLOWED_ORIGINS=https://meddxagentfrontend.vercel.app
```

Do not set a fixed `PORT` in Railway; the platform supplies it to the container.

After Railway assigns a public domain, verify these in order:

```text
GET /api/v1/health  -> HTTP 200
GET /api/v1/ready   -> HTTP 200
```

Only after both checks pass should the frontend production variable `VITE_MEDDX_API_URL` be set to the Railway service origin.

## Operational checks

Liveness:

```text
GET /api/v1/health
```

Returns HTTP 200 when the Tornado process is running.

Runtime readiness:

```text
GET /api/v1/ready
```

Returns HTTP 200 when environment variables required by the configured model classes are present. With the default clinical config, a missing `OAI_KEY` returns HTTP 503 and names only the missing variable, never its value.

## Clinical API

```text
POST /api/v1/clinical/sessions
GET  /api/v1/clinical/sessions/{session_id}
POST /api/v1/clinical/sessions/{session_id}/context
POST /api/v1/clinical/sessions/{session_id}/question
POST /api/v1/clinical/sessions/{session_id}/answer
POST /api/v1/clinical/sessions/{session_id}/history/finish
POST /api/v1/clinical/sessions/{session_id}/run
```

The intended sequence is:

```text
create session
-> generate one MEDDxAgent history question
-> submit the real patient response
-> repeat question/answer as needed
-> refresh final clinical context with examination/investigation findings
-> finish history
-> run DDxDriver RAG/diagnosis orchestration
-> read the real MEDDxAgent result snapshot
```

## Session lifetime

Clinical sessions are deliberately process-local in this first integration slice. This keeps the application adapter small and leaves the MEDDxAgent research implementation untouched.

Consequences:

- deploy one API process/worker for the first connected version
- a backend process restart invalidates in-flight `session_id` values
- durable multi-instance session storage is not part of this integration slice

This limitation should be handled explicitly during frontend connection/recovery rather than hidden behind fake persistence.

## Returned engine outputs

The clinical result contains only outputs produced by MEDDxAgent:

- `ranked_differential`
- `rationale`
- `dialogue_history`
- `rag_content`
- `intermediate_differentials`

No diagnosis confidence, management plan, classification, or fabricated evidence is generated by the application layer.
